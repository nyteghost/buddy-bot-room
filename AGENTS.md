## Application rules
- Settings belong in the app: any setting that doesn't have to exist before the server starts is a field in `SETTING_FIELDS` (`src/lib/settings.ts`) and is edited from the Setup window, not only through an environment variable. Saved values live in `BUDDY_DATA_DIR` (`app-settings.json`; secrets in `app-secrets.json`, mode 600, skipped by backups, never returned to the browser) and are laid over `process.env` by `settings.server.ts`, so modules keep reading `process.env` lazily (no module-level caching of those values). A real environment variable always wins. New integrations: add the fields, give the card its `group` id, and restart any timer or bot that reads its config once (`restartAfter`). Only stack-level settings (COMPOSE_PROFILES, Tailscale, Radicale password, Ollama runtime, accounts, data and backup folders) stay in Portainer. Server modules reachable from `vite.config.ts` must use relative imports (the config loader can't resolve `@/`).
- Keep window movement, visibility and layout persistence in browser-only workspace components; hiding windows must preserve mounted chat, tools and recorder state so work is not discarded.
- Assistant Mode is a separate browser-persisted switch (not a theme): any theme's cast keeps its name/voice but takes the shared assistant jobs, the office scene and machine helpers; legacy "assistant" theme maps to Linux theme + switch on.
- Pal voice playback via the server (Gemini) stays removed to save power; reading replies aloud is opt-in only (off by default) and uses the browser's own speechSynthesis (src/lib/voice.ts, tts.ts), so it costs no keys or server calls. It never starts without the user turning it on or tapping a speaker button.
- Assistant room movement uses one shared browser-only station choreography and activity renderer, so both modes stay visually in sync without invoking machine actions.
- Keep the current browser chat separate from named browser-only saved snapshots when signed out; optional Google sign-in syncs saved discussions and settings to the account.
- Run one streamed model call per character turn through `/api/chat`; browser orchestration controls rounds and cancellation, keeping each server request short.
- Keep agent identities and mode context rules in a shared browser-safe module; model prompts and gateway clients stay server-only.
- Keep character themes mutually exclusive in one browser-persisted store and shared persona catalog, preserving legacy preferences so sprites, names, prompts and voices stay consistent.
- Override AI SDK stream error logging to treat AbortError as cancellation, and return 499 at server boundaries; genuine failures remain reported so Stop does not trigger the runtime crash overlay.
- Compose chat surfaces with the installed AI Elements primitives and use semantic CSS tokens for the pixel-room visual theme.
- Draw character forms from browser-safe native pixel grids with semantic material palettes so visual detail is independent of display size.
- Store character mode on new replies and use one cancellable replay stream at a time; disable manual replay during discussion to prevent overlapping voices.
- Free engines (user keys, in-browser WebGPU, or Auto = keys first with per-turn WebGPU fallback when a key fails before any text) are chosen in a browser-persisted engine store; keys travel per request and are never stored server-side, and the local engine fetches its prompt from /api/chat (preparePrompt) so prompts stay server-authored.
- Signed-in users (Google) sync engine choice, theme and saved discussions to owner-only tables via requireSupabaseAuth server functions; free-engine keys are AES-GCM encrypted server-side with SETTINGS_ENCRYPTION_KEY. Signed-out users keep browser-only storage, so login stays optional.
- Linux Mode's machine access (PTY terminal, system stats, notes, file listing, self-update) lives only in Tauri commands in src-tauri/src/main.rs, wrapped by src/lib/linux.ts; pals receive this as read-only `linuxContext` text and every command/note they propose needs a user click — so the web build stays safe and nothing runs unattended.
- Work tools (Ungerboeck parsing, schedule reading, @deck solver, vendor links) run fully in the browser via src/lib/work-tools.ts, deck-solver.ts and lazily-loaded work-files.ts — no uploads leave the device and no AI call is needed.
- Mic recording (@record/@mic → Echo) uses browser MediaRecorder in src/components/mic-recorder.tsx and starts only on a user click; a clip is sent to /api/transcribe (one streamed multimodal call, speaker labels like Man 1/Woman 1) only when the user taps Transcribe.
- Schedule Excel uses exceljs via weekLayouts(); shared new/template formatting merges adjacent room cells only when full event signatures match, unmerges touched old room ranges before updates, and preserves engineer shifts to avoid lost or conflated events.
- Web search and Seerr run only through server routes (src/lib/search.server.ts, seerr.server.ts); their addresses and the Seerr API key come from server environment variables and are never read from the request or sent to the browser. Seerr requests always need a user click in SeerrDialog.
- Memories, notes and to-dos live only in browser storage (src/lib/workbench.ts); only memories and open to-dos are sent to pals, as clamped data (`memoryContext`) the server labels as non-instructions.
- Compare mode uses a neutral prompt (`neutral: true` on /api/chat, or the shared NEUTRAL_SYSTEM for Ollama/WebGPU) so results reflect the model, not a pal persona.
- Self-hosted only (BUDDY_SELF_HOSTED / BUDDY_PASSWORD / BUDDY_DATA_DIR): the password gate lives in src/lib/gate.server.ts and is applied by src/server.ts (production) and vite-self-hosted.ts (the Docker dev server); it must never read a request body except the login form, and is a no-op when BUDDY_PASSWORD is unset so Lovable is unaffected. Server-side chats (store.server.ts) load node:fs lazily and only when BUDDY_DATA_DIR is set.
- Anything copyable into a bug report goes through redact() (src/lib/redact.ts); never log API keys, passwords or request bodies.
- Jellyfin address/key come only from server environment variables (jellyfin.server.ts), like Seerr.
- Dungeon Master mode (src/lib/campaign.ts, dice.ts): while a campaign is active the first seated pal is the DM and the rest are party members, one pass per player action; the browser sends `campaign: {role, context}` and chat.server.ts swaps in the DM/party task. Dice are rolled in the browser with crypto randomness and the last few rolls go to the DM as context, so pals never invent rolls. Campaign state is browser-only.
- Unraid (src/lib/unraid.ts pure, unraid.server.ts I/O): read-only. The address, API key and ntfy URL come only from server env vars and never reach the browser or logs; a down alert needs two failed checks in a row; the watcher state lives on globalThis so the Vite plugin and routes share it.
- Accounts (self-hosted only; accounts.ts pure, accounts.server.ts I/O, gate.server.ts, account-local.server.ts): on when BUDDY_DATA_DIR is set and BUDDY_ACCOUNTS!=0. users.json holds PBKDF2 hashes; secret.key signs the HttpOnly session cookie; the first account is the owner (BUDDY_PASSWORD is its setup code). The gate handles /__me, /__signin, /__signup and /__logout for both the Vite dev plugin and src/server.ts. Never log or return hashes or the secret. Per-account settings live under BUDDY_DATA_DIR/accounts.
- Chat store with accounts: rows carry owner and shared, set only by the server (the browser can never choose them). GET returns your rows, shared rows and ownerless legacy rows; PUT refuses another owner's id; POST toggles sharing; per-owner cap of 300.
- Backups and scheduler (schedule.ts and backup.ts pure; backup.server.ts, scheduler.server.ts): BUDDY_BACKUP_DIR must be outside BUDDY_DATA_DIR (refused otherwise); backups are written to a .partial folder then renamed; only folders named pixelpals-YYYY-MM-DD-HHMM are ever pruned. Daily jobs use Intl time zones (BUDDY_TZ), never the OS zone. startScheduler() is a no-op unless a job is configured.
- Morning brief (brief.ts pure, brief.server.ts): built from the existing /api/trakt and /api/plex handlers plus the Unraid watcher snapshot and backup status; each part is optional and failures are skipped, never fatal. The daily pick is deterministic per day (no LLM). Sent via NTFY_URL by the scheduler at BRIEF_TIME.
- Note sync (notes-sync.ts pure, notes-sync.server.ts I/O): POST /api/notes-sync compares a note with Trakt; strictly read-only on Trakt, Trakt wins, never removes a user-typed mark, shows are only ▶. Auth is a session or a per-account Bearer token (stored as a SHA-256 hash; the gate accepts tokens for this one path only). Search lookups are capped at 25 lines.
- Trakt (trakt.ts pure, trakt.server.ts I/O): read-only on Trakt (GETs to api.trakt.tv only); with `plex=1` it also searches Plex (read-only) to mark which titles are already there, and Plex failures just leave titles unmarked; TRAKT_CLIENT_ID/TRAKT_ACCESS_TOKEN stay in server env. List and user names must pass isSlug before entering a URL. /next gives the pals the list as data and tells them to pick only from it.
- Installable app: public/manifest.webmanifest and the icons are listed in PUBLIC_FILES (gate.server.ts) so the browser can fetch them without cookies; keep that list to static, non-sensitive files. /?q= only prefills the message box and never sends.
- Plex (plex.ts pure, plex.server.ts I/O): read-only; PLEX_URL and PLEX_TOKEN come only from server env and are never returned to the browser. /watch gives the pals the library list as data and tells them to recommend only from it.

- Conversation modes (roundtable, broadcast, direct, solve, debate) each have their own window, chat (`chats[mode]`), draft and message box in room.tsx (`renderModeWindow`); `mode` is the window you are working in, `startIn(mode, …)` runs one at a time (`runLock`). Roles, debate sides and judge turns are sent to /api/chat as `role`, `side`, `verdict`, `summary`; the server owns the prompts.
- Living room (room-live.tsx, live-room.ts, progress.ts, progress-store.ts): the scene shows real weather, mail count, next calendar item, open tasks and server health from the existing owner-only endpoints (polled every 5 minutes while the room is open, anything unavailable is left out). Pal chatter is template text from that data, never an AI call. XP/level/streak live in the browser only; finishing tasks pays 10 XP (old finished tasks never pay out). Everything is read-only and clicking an object only opens its window.
- Real data for the pals (day-context.ts: calendar, unread mail subjects, open tasks, sent as `realData` only when the message asks for it) is answered by the user's own Ollama only (room.tsx `keepLocal`): server Ollama for cloud/auto engines, browser Ollama for auto-ollama; it never falls back to a cloud provider, and fails with a clear message if Ollama is unreachable.

## Local AI (server-side Ollama)
- Engine kind `local-server` sends `/api/chat` an `ollama-server` provider; the server calls `OLLAMA_URL` (never a browser-supplied URL). Model names are validated with `isModelName`.
- `/api/ollama` reports status, installed models and hardware, and pulls/removes models. Hardware comes from `os` plus `nvidia-smi` (or `LOCAL_VRAM_GB`); model suggestions are pure code in `src/lib/model-catalog.ts` and are tested.
- Claude (paid) and Local AI are never part of the free-key rotation; both are opt-in.
- Chat with your files: `smartRetrieve` (smart-docs.ts) reranks keyword candidates with Ollama embeddings via `/api/embed` and falls back to keyword search for 5 minutes after a failure. Automatic web lookup (`/web`, off by default) fetches `/api/search` and appends numbered results to `docContext` as data; `/status` (status.server.ts) reports reachability and never returns addresses or keys.
- Unattended asks (ask.server.ts: scheduled tasks in schedules.server.ts, Telegram in telegram.server.ts) use only the owner's saved free keys / Local AI; paid and custom providers are never used without a person in the room. Schedules are owner-only. The Telegram bot answers only TELEGRAM_CHAT_ID. Dictation (stt.server.ts) forwards audio to WHISPER_URL (env only), caps size, and never stores it.
- Saiyan (agent id `saiyan`) is the eighth pal: his persona is the same in every theme apart from role/tone, and he has real art per facing direction (src/assets/pals/saiyan/*.png via `facingArt`), so the office never mirrors/leans him; he is disabled by default in the room. Other pals use a single portrait per theme.
- Trakt write-back (trakt-write.server.ts) and Microsoft 365 (m365.server.ts) are owner-only and run only from a typed slash command, never from model output. M365 is read-only (calendar + unread mail subjects, Mail.ReadBasic so bodies are never requested); its summary uses Local AI only (`askPals({localOnly})`). Tokens live in the data volume with mode 600.
- Appearance (appearance.ts pure, appearance-store.ts hook): per-device `data-scheme`/`data-size` on <html>, synced as one short string key; the light scheme only applies when no themed cast class is on <html>.
- Local model "auto": a task set to `auto` becomes the marker `auto:<task>` (pickModel) and the server resolves it against /api/tags + hardware (`resolveLocalModel`, `bestInstalled`) in chat.server.ts and ask.server.ts; the browser never needs the installed list.
- Calendar and Mail windows (inbox.server.ts, ics.ts, imap.ts, imap.server.ts): owner-only and read-only. IMAP uses EXAMINE and header-only BODY.PEEK (never bodies, never marks read); ICS URLs and IMAP credentials come only from env. Never add send/delete/move to these.
- Weather (weather.server.ts, Open-Meteo, no key), reminders (reminders.server.ts, reminders.json, ticked by scheduler, pushed via `pushNotice`), `/event` (events.ts: client-side parse, `/api/ics` stateless download, Google/Outlook links; no calendar write access by design) all parse dates with when.ts (pure; wall time in BUDDY_TZ/browser zone). The brief reads calendar/mail through `calendarData`/`mailData` (inbox.server.ts) without a request; Mail "Draft a reply" sends only sender, subject and the user's words (mail-reply.ts) via the `pixelpals:ask` event to Echo.
- Setup window (setup.ts list + setup.server.ts tests, owner-only; never returns values), hide-secrets (privacy-store.ts + `.secret` class), search (find.ts; NOTE src/lib/search.ts is the web-search module, don't reuse the name), quick capture (capture.ts/capture.server.ts: Telegram prefixes and POST /api/capture; the gate lets a Shortcut token POST only there, and `op: take` needs a real owner session), repeating reminders (reminders.ts `takeRepeat`/`nextOccurrence`/`afterFiring`), weekly review (weekly.ts/weekly.server.ts, REVIEW_DAY/REVIEW_TIME), per-pal memory (`Workbench.pal`, `promptContext(w, max, agentId)`), saved prompts (prompts.ts + prompts-store.ts), backup restore (backup.server.ts `restoreBackup` makes pre-restore-<time> first; only names from the backup folder are accepted).
- Update alert: update.server.ts compares `__APP_COMMIT__` with GitHub `compare/<commit>...main` (cached 1h, owner-only, UPDATE_CHECK=0 disables); UpdateBanner shows only in the web build (desktop keeps update-popup.tsx); the scheduler pushes once per new latest commit (update-notified.txt).
- iPhone Reminders sync: Radicale container (packaging/radicale, profile `radicale`, plain htpasswd from env, owner_only rights) + caldav.ts (pure VTODO/multistatus/patch, keeps phone-made alarms by patching not rebuilding) + caldav.server.ts (config from RADICALE_*; never sent to the browser) + task-sync.ts (generic 3-way `syncPlan`, remote wins conflicts). Tasks: browser todos <-> `tasks` collection through POST /api/tasks (the browser keeps the agreed copy in localStorage; `TaskSync` component). Reminders: reminders.json <-> `reminders` collection from the scheduler (`tickCaldav`, every 2 min, base in caldav-reminders-base.json, goes through `updateReminders` so it can't race firing). Not verified against a real Radicale or iOS; e2e was against a stand-in server.

- Google Calendar (self-hosted): `src/lib/gcal.ts` (pure) and `gcal.server.ts` (owner-only OAuth + push, routes `/api/google`, `/api/google/start`, `/api/google/callback`). Token lives in `BUDDY_DATA_DIR/google-token.json`, excluded from backups. Keys are in-app settings (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`).

- Today planner (today.ts pure, today.server.ts I/O, /today route, today-planner.tsx): an ADHD day planner modelled on the user's whatnow fork (design reference only, no code copied). Tasks live in `BUDDY_DATA_DIR/today.json` on the server (not browser storage) so the installed home-screen app and Safari share one list. `/api/today` is owner-session only; `/api/today-capture` also accepts the per-account Bearer token but can only ADD an item (the gate allows it for that one path and POST only). Model calls go through `askPals` (free keys / Local AI only, never paid providers) and every reply is parsed defensively with a plain fallback, so nothing is lost when no model answers. Nudges (before calendar events, at check-in times) go through `pushNotice` from the scheduler tick; settings are TODAY_NUDGES, TODAY_NUDGE_LEAD, TODAY_CHECKINS. `src/routeTree.gen.ts` is committed: new routes must be added to it (the generator may not run in every environment).
