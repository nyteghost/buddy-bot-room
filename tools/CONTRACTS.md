# Pixel Pals agent-tooling contracts

Source of truth for the formats shared by the Claude-owned tools (`tools/core/**`,
branch `claude/dev-tooling`) and the ChatGPT-owned guardrails (`ownership.yml`,
`tools/guard/**`, `.github/workflows/pp-*.yml`, branch `chatgpt/dev-tooling`, PR #50).

Changes: propose in Issue #37 with a `pixel-pals-relay:v1` block; Claude updates this
file; the other side confirms. Additive optional fields are allowed without a version
bump; anything that changes or removes a field bumps the version (`/v2`).

## 0. Principles

1. **Claims vs evidence.** Every value is either `independent` (checked by a tool
   against git/GitHub) or `claimed` (copied from a developer's report or produced by
   the developer's own run). Tools label which. Only `verify-claim` turns a claim into
   a `VERIFIED` verdict, and only for the checks it can perform.
2. **Fail closed.** Missing, malformed, stale or pending evidence is `UNVERIFIED`,
   never `PASS`.
3. **Exact SHA.** Evidence counts only for the 40-hex commit it was produced on.
4. **No autonomy.** No tool or workflow calls an AI model, merges, deploys, or posts
   to GitHub on its own. `relay post` publishes only with an explicit `--confirm`.
5. **REST only.** Tools use the GitHub REST API (GraphQL is unavailable in some agent
   sessions). Backends: `gh api`, plain HTTPS (token from `GH_TOKEN`/`GITHUB_TOKEN`,
   or unauthenticated for this public repo), or fixtures for tests.

## 1. Exit codes (all tools)

| Code | Meaning |
|---|---|
| 0 | clean / every check passed |
| 1 | findings, failures, or anything UNVERIFIED |
| 2 | tool error (bad input, missing dependency, API failure) |

## 2. `ownership.yml` (owner: ChatGPT)

YAML 1.2 written in JSON-flow syntax; full-line `#` comments allowed.

```json
{"version": 1,
 "agents": {"<agent-id>": {"branches": ["<glob>"], "paths": ["<glob>"]}},
 "shared_readonly": ["docs/**"]}
```

- `agent-id`: `^[a-z0-9][a-z0-9-]{0,79}$` (also the relay `From:` value).
- Matching semantics live in `tools/guard/guardlib.py` (`matches`, `select_agent`).
  `tools/core` imports that module read-only rather than re-implementing it, so
  scope decisions are identical everywhere.
- **Trust:** verification always reads `ownership.yml` from the checkout that runs the
  tool (the trusted default branch in Actions), never from the claimed commit. A
  branch that edits `ownership.yml` without owning it fails `file-ownership`.

## 3. `pixel-pals-relay:v1` handoff block

```text
<!-- pixel-pals-relay:v1 -->
From: <agent-id>
To: <comma-separated recipients>
Status: <free text>
Branch: <branch>
Base: <base-branch> @ <40-hex merge-base sha>
Commit: <40-hex sha>
PR: <url>
Tests: <one-line summary; generated by `relay generate`>
Summary: <optional>
Next: <optional>
<!-- /pixel-pals-relay -->
```

- **Canonical** = valid `From` agent id + valid `Branch` + 40-hex lowercase SHA in
  `Commit` (fallback labels, in order: `Exact commit`, `Exact SHA`). Non-canonical
  blocks are legal history but can only ever be `UNVERIFIED`.
- Fields are read only between the opening and closing markers. Legacy blocks without
  a closing marker: the header ends at the first blank line.
- First occurrence of a field wins. Values may be wrapped in backticks.
- Generate new blocks with `tools/core/relay generate`; it fills fields from git and
  writes `UNVERIFIED` / `NOT RUN` for anything it cannot compute.
- **Authorship caveat:** all Issue #37 comments are posted from the owner's GitHub
  account, so `From:` is self-asserted. Verification checks *what* is claimed, not
  *who* claimed it.

## 4. `pp-test-results/v1` (written by `tools/core/pp-test`)

Default path `tools/out/test-results.json`.

```json
{"schema": "pp-test-results/v1",
 "branch": "...", "sha": "<40-hex>", "generated_at": "ISO-8601",
 "results": [{"name": "...", "command": "...",
              "evidence_level": "static|unit|integration|ci|native|hardware",
              "status": "pass|fail|skipped|not_run",
              "exit_code": 0, "duration_s": 0.0, "log_path": "...",
              "reason": "optional, why not_run/skipped"}],
 "dirty": false, "runner": "local|github-actions", "provenance": "claimed"}
```

Additive fields beyond the original contract: `dirty` (uncommitted changes, so the
results are not evidence for `sha`), `runner`, `provenance` (always `claimed`),
`results[].reason`.

## 5. `pp-findings/v1` (scope-check, security-lint, verify-claim)

Default path `tools/out/<tool>-findings.json`.

```json
{"schema": "pp-findings/v1", "tool": "scope-check|security-lint|verify-claim",
 "branch": "...", "sha": "...", "generated_at": "ISO-8601",
 "findings": [{"rule": "...", "severity": "blocker|high|medium|low|info",
               "file": "...", "line": 0, "message": "..."}]}
```

Additive fields used by `verify-claim`:

| Field | Meaning |
|---|---|
| `verdict` | `VERIFIED` (all independent checks verified), `FAILED` (any check failed), `UNVERIFIED` |
| `agent`, `repo`, `branch_head` | the claim being checked; current head of the branch |
| `checks[]` | `{check, status: verified/failed/unverified, evidence, provenance: independent/claimed}` |
| `ci` | `{state: pass/fail/pending/none, summary, checks[]}` for the exact SHA |
| `github_api_calls` | request count, for rate-limit awareness |

`verify-claim` checks: `assignment`, `commit-exists`, `on-branch`, `ci-exact-sha`,
`file-ownership`, and optionally `claimed-tests` (never better than `unverified`,
because self-reported results are not re-executed).

## 6. `verify-claim` CLI (owner: Claude; caller: `pp-relay-check.yml`)

```text
tools/core/verify-claim --branch <branch> --sha <40-hex> --agent <agent-id> --json
                        [--base beta] [--test-results FILE] [--output FILE]
tools/core/verify-claim --relay-comment <issue-comment-id> [--json]
```

Prints `pp-findings/v1` JSON on stdout with `--json`; also writes
`tools/out/verify-claim-findings.json`. Exit codes per section 1. The check named
`verify-relay` (the relay workflow's own job) is ignored as CI evidence.

## 7. Other machine-readable outputs

- `relay parse --json` → `{"schema": "pp-relay-index/v1", "provenance": "claimed", "relays": [...]}`
- `pp-context --json` → `{"schema": "pp-context/v1", ...}` (also `tools/out/context.json`)

## 8. Activation requirements (not done; owner decision)

`issue_comment` workflows run only from the repository **default branch (`main`)**.
PRs target `beta`, so `pp-relay-check.yml` cannot fire from either draft PR. Activation
needs, with explicit owner approval and security review:

1. `tools/core/**`, `tools/guard/**`, `ownership.yml` and `.github/workflows/pp-relay-check.yml`
   present on `main`.
2. Optional but recommended: pass `GH_TOKEN: ${{ github.token }}` to the verify step and
   grant `checks: read` + `statuses: read`, so the job is not limited to
   unauthenticated rate limits (60 requests/hour/IP; one verification uses ~6).
3. Until then, run `verify-claim` manually or from any agent session.
